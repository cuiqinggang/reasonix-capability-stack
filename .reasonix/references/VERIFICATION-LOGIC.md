# 验证逻辑完整协议(生态站权威版)

> 定位:本文件是 Reasonix 生态站重资料库对「执行与验证规则」的完整展开。
> 技能包内的 `skills/reasonix-mature-core/references/execution-verification.md` 是精简版(供子技能引用);
> 本文件是生态站级权威版,更详细:完整的三级状态标记、假失败/假成功陷阱清单、证据引用格式。
> 两文件评分与判定规则必须一致,不得出现两套标准。

## 1. 要避免的错误模式:失败-only 验证

坏模式:

- 真实执行确实发生了
- 工具调用确实成功
- 流程确实跑完
- 但验证器只搜索「异常字符串」,把每个周期都标成 FAIL

后果:制造假失败,掩盖真实系统状态;浪费修复轮次,破坏对后续阶段的判断。禁止。

验证必须同时检测成功信号与失败信号。

## 2. 双向验证模型

每个周期同时收集两类信号。

### 成功信号

| 信号 | 含义 | 例子 |
|------|------|------|
| 真实执行发生 | 有实际运行,不只是读配置/看文件 | 命令真实跑完、测试真实执行 |
| 工具/流程被调用 | 约定的工具或流程进入执行 | 审查子代理被调度、验证脚本被调用 |
| 产生了执行输出 | 由执行本身产生内容 | 测试 stdout、日志行、报告文件 |
| 输出有效 | 输出内容与预期断言匹配 | 断言通过、输出含预期标记 |

### 失败信号

| 信号 | 含义 |
|------|------|
| 执行无输出 | 跑了但没有任何产物 |
| mock/静态响应 | 返回固定内容,不是真实执行结果 |
| 流程未触发 | 该走的流程没走 |
| 工具未调用 | 声称调用但实际未调用 |

## 3. 加权评分

```text
execution_real    = +3   # 真实执行发生
tool_invoked      = +2   # 工具/流程被调用
output_generated  = +3   # 由执行产生了输出
output_valid      = +2   # 输出内容与断言匹配

mock_detected     = -4   # 发现 mock 或静态响应
missing_execution = -5   # 执行缺失
flow_bypass       = -5   # 流程被绕过
```

判定:

```text
score >= 5  => OK
score 1..4  => DEGRADED
score <= 0  => FAIL
```

注意:这是「周期级」判定;整个阶段的结论还要走 claim 级与验收级标记(见下)。

## 4. 三级状态标记

状态标记分三个层级,不可混用,不可自造词。

### 层级一:周期级 OK / DEGRADED / FAIL

每个验证周期(一次执行 + 一次检查)的输出,按 §3 评分判定。

### 层级二:claim 级 ACCEPTED / REJECTED / PENDING_EVIDENCE

Gate Review 对每条声明分类:

- `ACCEPTED`:证据充分、评分达标。
- `REJECTED`:证据不足,或证据与声明矛盾。
- `PENDING_EVIDENCE`:证据待补。不自动等于失败,但必须在报告中显式列出并给出补证路径。

### 层级三:验收级 PASS / PARTIAL / FAIL / PASS_WITH_KNOWN_ISSUES

阶段整体结论:

- `PASS`:全部 claim 通过,无未解决拒绝项。
- `PASS_WITH_KNOWN_ISSUES`:存在已知失败,但每一条都能在 `FAILURE-MODES.md` 中对应(known_failures 清单),且不阻塞本阶段目标。
- `PARTIAL`:部分 claim 通过,其余待补或降级。
- `FAIL`:存在未解决拒绝项或新失败。

### 三级联动规则

1. 周期级 OK 不自动推导验收级 PASS:多个 OK 周期只说明各周期执行有效;整体验收仍需逐条 claim 对比证据。
2. 验收级 PASS 要求:claim 级无未解决 REJECTED、无未解决 blocker。
3. 存在未解决 REJECTED 时,只能报 BLOCKED / FAIL,不得报 PASS。

## 5. 假失败陷阱(把真实状态误判为失败)

### T-01 失败-only 验证

- 现象:所有周期全标 FAIL,但真实执行与产物都在。
- 检测:检查验证器是否只搜索异常字符串;统计成功信号收集个数(应为非零)。
- 规避:按 §2 同时收集两类信号,按 §3 加权评分。

### T-02 stderr 误读

- 现象:工具把进度、状态、警告写到 stderr,验证器把 stderr 当作失败依据。
- 检测:查看命令退出码与 stderr 原文,区分「进度输出」与「真实错误」。
- 规避:以退出码 + 产物 + 断言为准;stderr 中的进度行不作为失败信号。

### T-03 超时即 FAIL

- 现象:慢工具触发超时,未等执行结果就被判失败。
- 检测:重跑一次并加大超时,观察是否成功。
- 规避:超时先记 DEGRADED 或 PENDING_EVIDENCE,先重试;不直接 FAIL。

### T-04 未知即 FAIL

- 现象:证据缺失或状态未知,直接被当成失败。
- 规避:UNKNOWN → PENDING_EVIDENCE,给出补证路径;未知不自动等于失败。

### T-05 上下文截断误判

- 现象:长输出被截断,验证器只看到尾部片段,误判结果。
- 检测:大输出落盘后按关键片段检索,或做校验和比对。
- 规避:不以截断视图作结论;需要时分段读取验证。

## 6. 假成功陷阱(把未验证当通过)

### S-01 mock / 静态响应

- 现象:返回固定内容,多次执行结果逐字节相同;或验证环境里 mock 未隔离。
- 检测:对比两次执行输出哈希;检查是否命中 mock 配置。
- 规避:mock 必须显式标记并隔离;验证目标必须走真实执行。

### S-02 有响应 ID 但内容为空

- 现象:调用返回了响应 ID(传输层成功),但内容为空。
- 检测:检查内容是否非空,而不是只看 ID 是否存在。
- 规避:空内容只记 PARTIAL;重试小提示词;仍空则如实报告,不 PASS。

### S-03 配置-only 证明

- 现象:只验证配置文件/索引/设置存在,就声称「已生效/已验证」。
- 检测:核对证据类型是否仅为 `active_config_confirmed`,而非 `live_call_verified`。
- 规避:区分声明类型;需要「真实执行验证」的声明,必须实际运行命令/调用。

### S-04 缓存当作新执行

- 现象:验证复用了旧结果缓存,没有产生新执行。
- 检测:检查输出时间戳、确认命令真的重新运行。
- 规避:验证命令每次真实运行;结果落盘带时间戳。

### S-05 无断言的 always-pass 测试

- 现象:测试函数没有真实断言,永远返回成功。
- 检测:审查测试代码断言数;故意注入错误,观察测试是否变红。
- 规避:每个测试至少一个有效断言;提交前做「必失败注入」自检。

### S-06 文件存在 ≠ 内容正确

- 现象:报告/输出文件存在,但内容是空壳、占位或陈旧。
- 检测:打开文件检查关键内容,不只看文件系统存在性。
- 规避:文件证据必须带内容断言或关键片段引用。

### S-07 报告/脚本/打包产物本身当验收

- 现象:因为「报告写出来了」「脚本退出码 0」「打包产物存在」就宣布通过。
- 规避:这些都只是输入材料;验收必须逐条对比 claim 与 evidence。

### S-08 放宽验收标准

- 现象:为让阶段通过,临时降低验收标准或改动判据。
- 规避:验收标准在验证开始前定死;被拒 claim 走 Repair Loop,不改标准。

## 7. 验收规则(不可妥协)

1. 未知不自动等于 FAIL;任何异常也不自动等于 FAIL。
2. 报告文件、脚本输出、打包产物本身不构成验收。
3. 验收 = 逐条对比 claim 与 evidence,按 §4 分层标记。
4. 被拒 claim 必须进入 Repair Loop,或保持显式 unresolved。
5. 存在未解决拒绝项或阻塞项时,不得声明 PASS。
6. 验收标准不可被证据反向修改(先定标准,后看证据)。
7. 修复轮次以「重跑验证 + 新证据」为据,不以「声称修好」为据。

## 8. 每周期必需输出

```json
{
  "cycle_id": "CYCLE-07",
  "execution_verified": true,
  "flow_verified": true,
  "tool_verified": true,
  "output_valid": true,
  "score": 10,
  "status": "OK"
}
```

周期输出、Gate Review 的 claim 清单与验收结论分别存 `.reasonix/state/gate-reviews/` 与 `.reasonix/reports/`。

## 9. 证据引用格式

- 文档证据:`<相对路径>:<行号>`,例如 `references/ASSET-SEARCH-PATHS.md:41`。
- 命令证据:`$ <命令>` + 一行结果摘要;命令必须是实际运行过的。
- 测试证据:`<命令> | 通过/失败/错误/跳过 | <断言数> | <耗时>`。
- 状态证据:状态标记词表内的显式值,不允许自造词。
- 每条证据须可被独立复查(路径真实存在、命令可重跑)。
